Windows Single Sign-On for Ignition Perspective

How a domain user opens an Ignition Perspective page and is signed in automatically — no username or password — using Active Directory, AD FS (OpenID Connect) and Kerberos. Complete build record, replication steps and a troubleshooting guide from the working lab.

1 · Overview

What was built, and the one design decision everything else follows from.

Key fact: Ignition cannot do Kerberos / "Windows login" by itself. The old “SSO Enabled” option of the Active Directory user source was disabled in Ignition 8.1.17 for a security vulnerability and is deprecated. The supported way to get silent Windows sign-in is to put an external identity provider (IdP) in front of Ignition. Here that IdP is AD FS, speaking OpenID Connect. AD FS is the component that actually performs the Windows (Kerberos) authentication; Ignition only trusts the token AD FS returns.

What you end up with

  • An AD domain controller that also hosts DNS, an Enterprise Certificate Authority and AD FS.
  • Two TLS certificates issued by your own CA: one for AD FS, one for Ignition (both with the right Subject Alternative Names).
  • An Ignition 8.3 Gateway on HTTPS (port 8043) using that certificate and trusting your CA.
  • An OIDC client in AD FS for Ignition, and an ADFS identity provider in Ignition mapped to AD attributes.
  • A Perspective project that requires authentication and shows who is signed in.
  • A Group Policy that makes domain browsers send Windows credentials to AD FS automatically.

Architecture

Everything in this lab (DC, CA, DNS, AD FS, Ignition) runs on one server, DC01. That is fine for a lab; see Production notes for how to split it.

3 · How a login works

Understanding this sequence makes every problem below easy to place.

  1. The user opens https://ignition.example.local:8043/data/perspective/client/SSOTest. The project requires the Authenticated security level, so Perspective shows “You must log in to continue” → Continue to log in.
  2. Ignition redirects the browser to AD FS: /adfs/oauth2/authorize/ with client_id=ignition-perspective, the redirect URI and scopes openid profile email allatclaims.
  3. AD FS answers with its Windows-integrated endpoint /adfs/oauth2/authorize/wia. That only works silently if (a) the browser considers AD FS an intranet site, (b) the browser is allowed to use Negotiate/Kerberos to that host, and (c) AD FS accepts that browser’s User-Agent for WIA.
  4. The browser requests a Kerberos service ticket for host/adfs.example.local (the SPN on the gMSA) using the user’s Windows logon, and presents it. AD FS validates it with AD.
  5. AD FS builds the token using the issuance transform rules (UPN, e-mail, sAMAccountName as unique_name, AD groups as role) and sends the browser back to the Ignition redirect URI with an authorization code (form post).
  6. Ignition’s Gateway — server to server — calls AD FS’s token endpoint (needs the client secret and must trust the AD FS certificate), validates the signed ID token, and applies User Attribute Mapping.
  7. The Perspective session now has session.props.auth.user.userName, .email, .roles and the view renders them.
Where each failure shows up Steps 1–2 failing = Ignition/IdP config. Step 3 stuck on a password form = browser/GPO/User-Agent/SPN. Step 6 failing = Ignition cannot reach or trust AD FS (DNS, CA trust, secret). That mapping is how the Troubleshooting section is organised.

4 · Prerequisites & decisions

Check these before you start. The reasons are what you will need when something is different in your environment.

Needed

  • An AD domain, a DNS zone for it, and an Enterprise Root/Sub CA (AD CS) whose certificate is trusted by all domain machines (automatic for an Enterprise CA).
  • An elevated Windows PowerShell 5.1 session as a domain admin (an un-elevated admin token gives Access denied for DNS/CA/AD FS commands).
  • The Ignition 8.3 Windows installer and the Designer Launcher (both from inductiveautomation.com; the download page needs a registration form).
  • Clients that are domain-joined, use your DNS, and where the user logs in with a domain account.
  • Accurate time everywhere (Kerberos tolerates only ~5 min skew).

Decisions made here

  • OIDC, not SAML. Ignition supports both; OIDC needs no extra signing-certificate handling.
  • Use host names, never IPs. Kerberos and the intranet-zone rule only work with a DNS name (adfs.…, ignition.…).
  • Ignition on 8043. AD FS must own 443 on its host, so the one-server lab puts Ignition on 8043 and Windows Admin Center on 6443.
  • gMSA as the AD FS service account (no password to manage).
  • Server certs from your own CA, with SAN — modern browsers and Java both require SAN.
  • No Ignition “user source” for SSO: in 8.3 an external IdP maps claims to users and roles directly.

1DNS

Create the two host names, and make the server use its own DNS.

Kerberos, the browser’s intranet-zone decision, and both TLS certificates all depend on host names. Create an A record for each service in your AD-integrated zone, both pointing at the server.

PS> on the DC
$zone = 'example.local'
$ip   = '10.0.0.10'
foreach ($h in 'adfs','ignition') {
  if (-not (Get-DnsServerResourceRecord -ZoneName $zone -Name $h -ErrorAction SilentlyContinue)) {
    Add-DnsServerResourceRecordA -ZoneName $zone -Name $h -IPv4Address $ip
  }
}
Get-DnsServerResourceRecord -ZoneName $zone -RRType A | Where HostName -in 'adfs','ignition'

Make sure the server resolves through itself

A domain controller must list itself first in its DNS client settings. In this lab it pointed at 10.0.0.1 (the Hyper-V host), so the DC’s own scripts could not resolve adfs.example.local even though its DNS server answered correctly.

PS>
Set-DnsClientServerAddress -InterfaceAlias 'Ethernet 2' -ServerAddresses '10.0.0.10','10.0.0.1'
Clear-DnsClientCache
Resolve-DnsName adfs.example.local     # must return 10.0.0.10
Resolve-DnsName ignition.example.local
Clients too Every client (and any separate Ignition server) must use this DNS server, otherwise it cannot resolve adfs.example.local. The public domain ignition.example.com that was used at first is not part of this setup; use a name inside your AD DNS zone.

2Certificates

Two server certificates from your CA: one for AD FS, one for Ignition. The two are created differently on purpose.

Why two different methods? The built-in WebServer template is machine-only and its private key is not exportable. That is perfect for AD FS (the key stays in the Windows store). Ignition, however, is a Java application and needs the key as a file — so its key and request are created with Ignition’s own keytool, and the CA only signs it.

2.1 Let the server request from the WebServer template

The first attempt failed with CERTSRV_E_TEMPLATE_DENIED because Get-Certificate … -CertStoreLocation Cert:\LocalMachine\My enrolls as the computer account, and that account was not allowed to enroll. Grant Domain Controllers (the group the DC’s computer account is in) the Enroll right.

PS> elevated, Enterprise Admin
Import-Module ActiveDirectory
$cfg = (Get-ADRootDSE).configurationNamingContext
$dn  = "CN=WebServer,CN=Certificate Templates,CN=Public Key Services,CN=Services,$cfg"
dsacls $dn /G "EXAMPLE\Domain Controllers:CA;Enroll"
# Verify the template is published on the CA
certutil -CATemplates | Select-String WebServer
Note Granting Enroll on a CA template is a PKI permission change. In this lab “Domain Admins” already had Enroll (it was granted twice by mistake, which is harmless). Remove duplicates in certtmpl.msc → WebServer → Security if you want it tidy. Do not “fix” the problem by enabling EDITF_ATTRIBUTESUBJECTALTNAME2 on the CA — that is a well-known privilege-escalation hole.

2.2 AD FS certificate (machine store)

AD FS requires the certificate subject and a SAN equal to the federation service name. certauth.adfs… is only needed for certificate authentication; it is harmless to include.

PS>
Get-Certificate -Template WebServer `
  -DnsName 'adfs.example.local','certauth.adfs.example.local' `
  -SubjectName 'CN=adfs.example.local' `
  -CertStoreLocation Cert:\LocalMachine\My

Get-ChildItem Cert:\LocalMachine\My | Where Subject -eq 'CN=adfs.example.local' |
  Select Subject,Thumbprint,NotAfter,HasPrivateKey,DnsNameList | fl

Write the thumbprint down — Install-AdfsFarm in Step 3 needs it (here A1B2C3D4E5F60718293A4B5C6D7E8F9012345678).

2.3 Export the CA certificate (clients and Ignition need it)

PS>
$ca = Get-ChildItem Cert:\LocalMachine\My | Where Subject -like 'CN=example-CA*' | Select -First 1
Export-Certificate -Cert $ca -FilePath C:\adfs-setup\example-ca.cer -Type CERT
Gotcha certutil -ca.cert file.cer fails inside PowerShell with “Expected no more than 1 args” because the dot is parsed as a member access. Use Export-Certificate as above, or quote it: certutil '-ca.cert' file.cer.

2.4 Ignition certificate (key made by keytool, signed by the CA)

Do this after Ignition is installed (Step 7), because it uses Ignition’s bundled Java keytool. It is listed here so all certificate work is in one place.

a) Create the key pair and CSR with a SAN

PS>
$kt = 'C:\Program Files\Inductive Automation\Ignition\lib\runtime\jre-win\bin\keytool.exe'
$d  = 'C:\adfs-setup\ign'; New-Item -ItemType Directory -Force $d | Out-Null
$pw = -join ((48..57)+(65..90)+(97..122) | Get-Random -Count 24 | % {[char]$_})
Set-Content "$d\keystore-password.txt" $pw -Encoding ASCII
icacls "$d\keystore-password.txt" /inheritance:r /grant:r "Administrators:F" "SYSTEM:F" | Out-Null

& $kt -genkeypair -alias ignition -keyalg RSA -keysize 2048 -sigalg SHA256withRSA -validity 730 `
  -dname "CN=ignition.example.local, O=Example, OU=IT, C=US" `
  -ext "SAN=dns:ignition.example.local" -ext "EKU=serverAuth" `
  -keystore "$d\ignition.p12" -storetype PKCS12 -storepass $pw -keypass $pw

& $kt -certreq -alias ignition -keystore "$d\ignition.p12" -storetype PKCS12 -storepass $pw `
  -ext "SAN=dns:ignition.example.local" -file "$d\ignition.csr"

certutil -dump "$d\ignition.csr" | Select-String 'DNS Name'   # must show the SAN
Why not Ignition’s own “Create CSR” wizard? It produced a request with an empty Subject Alternative Name. The CA signed it, but Edge/Chrome reject a certificate with no SAN (ERR_CERT_COMMON_NAME_INVALID). Always check the CSR with certutil -dump before submitting.

b) Submit it to the CA as the computer account

The template is machine-only, so a request submitted as you fails with “This type of certificate can be issued only to a computer”. A one-shot scheduled task running as SYSTEM submits as the computer account:

PS>
$cmd = 'certreq -submit -f -q -config "DC01.example.local\example-CA" ' +
       '-attrib "CertificateTemplate:WebServer" C:\adfs-setup\ign\ignition.csr C:\adfs-setup\ign\ignition-signed.cer'
$a = New-ScheduledTaskAction -Execute cmd.exe -Argument "/c $cmd"
$p = New-ScheduledTaskPrincipal -UserId SYSTEM -LogonType ServiceAccount -RunLevel Highest
Register-ScheduledTask -TaskName TmpCsr -Action $a -Principal $p -Force | Out-Null
Start-ScheduledTask TmpCsr; Start-Sleep 10
Unregister-ScheduledTask TmpCsr -Confirm:$false
certutil -dump C:\adfs-setup\ign\ignition-signed.cer | Select-String 'DNS Name|NotAfter'

c) Put the signed certificate (and CA) into the keystore

PS>
$pw = (Get-Content "$d\keystore-password.txt").Trim()
& $kt -importcert -noprompt -trustcacerts -alias example-ca -file C:\adfs-setup\example-ca.cer -keystore "$d\ignition.p12" -storetype PKCS12 -storepass $pw
& $kt -importcert -noprompt -trustcacerts -alias ignition     -file "$d\ignition-signed.cer"      -keystore "$d\ignition.p12" -storetype PKCS12 -storepass $pw
& $kt -list -keystore "$d\ignition.p12" -storetype PKCS12 -storepass $pw   # expect: PrivateKeyEntry + trustedCertEntry

d) Convert to the three PEM files Ignition’s SSL wizard wants

Ignition 8.3’s “I have all the items” path wants the key as PKCS#8 PEM, plus the server certificate and the CA certificate as PEM. There is no openssl on the server, so .NET’s CNG API does the conversion (Windows PowerShell 5.1):

PS>
Add-Type -AssemblyName System.Security
$flags = [Security.Cryptography.X509Certificates.X509KeyStorageFlags]::Exportable
$col = New-Object Security.Cryptography.X509Certificates.X509Certificate2Collection
$col.Import("$d\ignition.p12", $pw, $flags)
$cert = $col | Where HasPrivateKey | Select -First 1
$rsa  = [Security.Cryptography.X509Certificates.RSACertificateExtensions]::GetRSAPrivateKey($cert)
$blob = $rsa.Key.Export([Security.Cryptography.CngKeyBlobFormat]::Pkcs8PrivateBlob)
function ToPem($b,$label){ "-----BEGIN $label-----`n" + [Convert]::ToBase64String($b,'InsertLineBreaks') + "`n-----END $label-----`n" }
$ascii = [Text.Encoding]::ASCII
[IO.File]::WriteAllText("$d\ignition-key.pem",  (ToPem $blob 'PRIVATE KEY'),       $ascii)
[IO.File]::WriteAllText("$d\ignition-cert.pem", (ToPem $cert.RawData 'CERTIFICATE'), $ascii)
$caCert = New-Object Security.Cryptography.X509Certificates.X509Certificate2 'C:\adfs-setup\example-ca.cer'
[IO.File]::WriteAllText("$d\example-ca.pem",  (ToPem $caCert.RawData 'CERTIFICATE'), $ascii)
icacls "$d\ignition-key.pem" /inheritance:r /grant:r "Administrators:F" "SYSTEM:F" | Out-Null
Protect the key ignition-key.pem and ignition.p12 are the Gateway’s private key. In this lab the key text was pasted into Ignition via the browser and also appeared in the working notes; treat that key as exposed and regenerate it (repeat 2.4) before using this for anything real. Delete the files from C:\adfs-setup\ign afterwards — Ignition keeps its own copy.

3AD FS install

KDS root key → service account → role → free port 443 → farm → browser User-Agent list.

3.1 KDS root key and the gMSA

A group-managed service account needs a KDS root key in the forest. A new key normally becomes usable after 10 hours (so every DC has replicated it). On a single DC lab you can back-date it.

PS>
if (-not (Get-KdsRootKey)) { Add-KdsRootKey -EffectiveTime ((Get-Date).AddHours(-10)) }   # lab only; production: wait 10 h
Get-KdsRootKey | Select KeyId,EffectiveTime

New-ADServiceAccount -Name adfs-svc -DNSHostName adfs.example.local `
  -PrincipalsAllowedToRetrieveManagedPassword 'DC01$'

# Windows Server 2025 does not allow RC4 - make the account AES-only (value 24)
Set-ADServiceAccount adfs-svc -KerberosEncryptionType AES128,AES256
Get-ADServiceAccount adfs-svc -Properties msDS-SupportedEncryptionTypes | Select Name,'msDS-SupportedEncryptionTypes'
The encryption-type trap A fresh gMSA has msDS-SupportedEncryptionTypes = 28 (RC4 + AES). The server only supports AES (24), so Install-ADServiceAccount fails with “The provided context did not match the target” and the event log (Microsoft-Windows-ManagedServiceAccount/Operational, IDs 9000–9002) says “not all the supported encryption types of the account are supported by the local machine”. Setting the account to AES-only fixes it. (A reboot is also needed after the account is created so the server’s Kerberos ticket reflects its permission — or run klist purge -li 0x3e7.)

3.3 Free port 443 (Windows Admin Center was using it)

AD FS (HTTP.sys) must listen on 443. In this lab Windows Admin Center (WAC) was already bound to 443 through Kestrel. Move WAC to 6443 by editing its settings file in two places and restarting its service:

PS>
$f = 'C:\Program Files\WindowsAdminCenter\Service\appsettings.json'
Copy-Item $f C:\adfs-setup\appsettings.json.bak -Force
$t = Get-Content $f -Raw
$t = $t.Replace('"Url":  "https://*:443"','"Url":  "https://*:6443"').Replace('"https://+:443"','"https://+:6443"')
Set-Content $f $t -Encoding UTF8
Restart-Service WindowsAdminCenter
Get-NetTCPConnection -State Listen | Where LocalPort -in 443,6443 |
  Select LocalPort,@{n='Proc';e={(Get-Process -Id $_.OwningProcess).Name}}
After this WAC is at https://<server>:6443 and its old firewall rule (443) no longer matches — add a rule for 6443 if you use WAC remotely. Its self-signed certificate had also expired (May 2026); that is cosmetic but worth replacing. If your server has no WAC, skip this step. Use Get-NetTCPConnection -LocalPort 443 to find whatever else holds 443.

4Register Ignition in AD FS

An application group with a confidential server application (the OIDC client) and a web API (so claims reach the ID token).

Why a web API too? The claims in the ID token come from the issuance transform rules of the relying party the client asks for. Giving the Web API the same identifier as the client id makes AD FS use its rules for the ID token, so UPN, e-mail, username and groups arrive. Without it the token contains only a few default claims.
PS>
$grp      = 'Ignition SCADA'
$clientId = 'ignition-perspective'
$redirect = 'https://ignition.example.local:8043/data/federate/callback/oidc'   # exactly Ignition's value

New-AdfsApplicationGroup -Name $grp -ApplicationGroupIdentifier $clientId           # NOTE: New-, not Add-

$app = Add-AdfsServerApplication -Name 'Ignition Gateway - Server app' `
         -ApplicationGroupIdentifier $clientId -Identifier $clientId `
         -RedirectUri $redirect -GenerateClientSecret
# The secret is shown only once - store it with a locked-down ACL:
Set-Content C:\adfs-setup\ignition-client-secret.txt $app.ClientSecret -Encoding ASCII
icacls C:\adfs-setup\ignition-client-secret.txt /inheritance:r /grant:r "Administrators:F" "SYSTEM:F" | Out-Null

Add-AdfsWebApiApplication -Name 'Ignition Gateway - Web API' `
  -ApplicationGroupIdentifier $clientId -Identifier $clientId -AccessControlPolicyName 'Permit everyone'

$rules = @'
@RuleName = "AD attributes"
c:[Type == "http://schemas.microsoft.com/ws/2008/06/identity/claims/windowsaccountname", Issuer == "AD AUTHORITY"]
 => issue(store = "Active Directory", types = ("http://schemas.xmlsoap.org/ws/2005/05/identity/claims/upn", "http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress", "http://schemas.xmlsoap.org/ws/2005/05/identity/claims/name"), query = ";userPrincipalName,mail,sAMAccountName;{0}", param = c.Value);

@RuleName = "AD groups as roles"
c:[Type == "http://schemas.microsoft.com/ws/2008/06/identity/claims/windowsaccountname", Issuer == "AD AUTHORITY"]
 => issue(store = "Active Directory", types = ("http://schemas.microsoft.com/ws/2008/06/identity/claims/role"), query = ";tokenGroups;{0}", param = c.Value);
'@
Set-AdfsWebApiApplication -TargetName 'Ignition Gateway - Web API' -IssuanceTransformRules $rules

Grant-AdfsApplicationPermission -ClientRoleIdentifier $clientId -ServerRoleIdentifier $clientId `
  -ScopeNames 'openid','profile','email','allatclaims'

5Group Policy for the browsers

This is what turns “password form” into “silent”. Without it, Edge/Chrome do not send the user’s Windows credentials to AD FS.

Two things are required on each client, and one GPO provides both:

  • Intranet zone — Windows/Edge only auto-sign-in to sites in the Local Intranet zone. A name with a dot (adfs.example.local) is not an intranet site by default, so map it explicitly (zone value 1).
  • Allow-list for Negotiate — Edge and Chrome need AuthServerAllowlist to attempt Kerberos/NTLM against a fully-qualified host.
PS>
Import-Module GroupPolicy
$name = 'SSO - AD FS Intranet Zone'
$gpo  = Get-GPO -Name $name -ErrorAction SilentlyContinue
if (-not $gpo) { $gpo = New-GPO -Name $name -Comment 'Treat AD FS as intranet so browsers send Windows credentials (Kerberos) for SSO' }
$site = 'adfs.example.local'

$zk = 'HKLM\Software\Policies\Microsoft\Windows\CurrentVersion\Internet Settings\ZoneMapKey'
Set-GPRegistryValue -Name $name -Key $zk -ValueName "https://$site" -Type String -Value '1'
Set-GPRegistryValue -Name $name -Key $zk -ValueName "http://$site"  -Type String -Value '1'

A · Build & platform

Commands fail with “Access is denied” though I am Administrator shell

Cause: an un-elevated token (UAC filters the built-in Administrator; IsInRole(Administrator) returns False). DNS, CA, AD FS and feature installs all need elevation.

Fix: start PowerShell / the tool “as administrator”. Check with ([Security.Principal.WindowsPrincipal][Security.Principal.WindowsIdentity]::GetCurrent()).IsInRole([Security.Principal.WindowsBuiltInRole]::Administrator). Side effect: Get-KdsRootKey returns nothing when not elevated, which looks like “key missing”.

Server can’t resolve adfs.example.local although the DNS record exists DNS

Cause: the DC’s DNS client pointed at another resolver (the Hyper-V host 10.0.0.1). The DNS server answered correctly (Resolve-DnsName … -Server 127.0.0.1 worked).

Fix: Set-DnsClientServerAddress -InterfaceAlias 'Ethernet 2' -ServerAddresses '10.0.0.10','10.0.0.1' then Clear-DnsClientCache.

Port 443 already in use before installing AD FS AD FS

Cause: Windows Admin Center (Kestrel) was bound to *:443. Find the owner: Get-NetTCPConnection -LocalPort 443 -State Listen | % { (Get-Process -Id $_.OwningProcess).Name }.

Fix: move WAC to 6443 in appsettings.json (Kestrel.Endpoints.WindowsAdminCenter.Url and HttpSysUrls) and restart WindowsAdminCenter. Not recommended: running AD FS on a non-443 port (every URL, redirect and discovery value then needs the port).

Install-ADServiceAccount: “The provided context did not match the target” gMSA

Cause 1 (the real one here): encryption types. Event 9001: not all the supported encryption types of the account are supported by the local machine. Server 2025 has RC4 off; the gMSA defaulted to 28.

Fix 1: Set-ADServiceAccount adfs-svc -KerberosEncryptionType AES128,AES256 (value 24), klist purge -li 0x3e7, retry. Event 9000 “Netlogon failed to retrieve the password … Object Name not found” usually follows from the same cause.

Cause 2: the computer is not in PrincipalsAllowedToRetrieveManagedPassword, or its Kerberos ticket pre-dates that change → reboot once. Cause 3: KDS root key missing/not yet effective (Get-KdsRootKey).

CERTSRV_E_TEMPLATE_DENIED / “can be issued only to a computer” certificates

Cause: WebServer is a machine template. Get-Certificate into LocalMachine\My enrolls as the computer account, which lacked Enroll. Requesting into CurrentUser\My as an admin fails with “can be issued only to a computer”.

Fix: give Domain Controllers Enroll on the template (Step 2.1) and request into the machine store; for an externally generated CSR, submit it as SYSTEM via a one-shot scheduled task (Step 2.4b).

Certificate has “No alternative name” — browser says the name does not match certificates

Cause: Ignition’s built-in CSR form has no SAN field, so the CA issues a certificate with an empty SAN. Browsers and Java need the host name in the SAN.

Fix: create the CSR with keytool … -ext SAN=dns:host (Step 2.4a), check certutil -dump file.csr shows DNS Name=…, and verify the issued cert the same way. Do not enable the CA’s EDITF_ATTRIBUTESUBJECTALTNAME2 flag.

Gateway logs “Resource bytes are null”; hand-made views never load Ignition files

Cause: a template containing the word files was filled with -replace 'FILE','view.json'. PowerShell’s -replace is case-insensitive, so it also rewrote the JSON key "files" to "view.jsons".

Fix: the correct resource.json is {"scope":"G","version":1,"restricted":false,"overridable":true,"files":["view.json"],"attributes":{}}. Use .Replace() (case-sensitive) or -creplace. Then Scan File System or restart.

Silent installers return 0 but nothing is installed install

Ignition --mode unattended and Designer Launcher -q did not complete in this environment (the quiet run waited for a window). Run both installers interactively.

certutil -ca.cert: “Expected no more than 1 args” PowerShell

PowerShell splits at the dot. Quote it (certutil '-ca.cert' out.cer) or use Export-Certificate.

A wrong name makes every following command fail with “No application group found with identifier …” and a script can still write an empty secret file — delete it and re-run.

After “Sign out” the user is signed straight back in behaviour

Expected with SSO: logging out of Ignition does not end the AD FS/Windows session, so the next visit re-authenticates silently. Single logout is not configured. Users who must switch identity need to sign out of Windows or use a different browser profile; Always ask the IdP to re-authenticate (project setting) forces a prompt.

Production & security notes

What is fine for a lab, and what should change before real use.

Architecture

  • Put AD FS, the CA, WSUS, Ignition and Windows Admin Center on separate servers; keep the DC for AD/DNS only. Microsoft advises against a CA or AD FS on a domain controller.
  • Run AD FS on ≥2 nodes behind a load balancer; use a SQL back end if you need more than a few nodes. Publish via a proxy (Web Application Proxy / reverse proxy) only if you need external access.
  • Use a CA hierarchy (offline root + issuing CA) and publish HTTP CDP/AIA so every client can validate.

Secrets & keys

  • The Ignition private key was displayed in the build session → regenerate the Ignition certificate and key.
  • Plain-text files in C:\adfs-setup (ignition-client-secret.txt, ssotest-password.txt, ign\*.pem/.p12/password, scripts and logs) must be moved to a vault or deleted; keep only what you need.
  • Store the client secret using Ignition’s Secret Providers instead of “Embedded”. Rotate it on a schedule.
  • Replace the lab test user; use named domain groups and map them to Security Levels/roles.

Operations

  • Certificate expiries: AD FS service cert 2028-10-01, Ignition cert 2028-10-01, AD FS token-signing/decrypting 2027-10-02 (self-managed, auto-rollover on). Calendar them.
  • After renewing the AD FS cert: Set-AdfsSslCertificate -Thumbprint … on every node, restart adfssrv.
  • Back up AD FS (system state / WID), the CA (database + key), and an Ignition Gateway backup (Platform → Backup & Restore).
  • Re-apply the Java CA import and Designer JVM flag after Ignition upgrades.
  • Enable Force Secure Redirect and keep 8088 closed; consider disabling HTTP completely.
  • Licence Ignition (trial resets every 2 h).
Not covered Multi-factor authentication, single logout, device registration / Workplace Join, SAML, and non-Windows/non-domain clients (those fall back to the AD FS forms login). AD FS can add MFA providers; Ignition then simply receives the same token.

function Label($name,$x,$y,$w,$h,$expr,$size,$bold,$color,$text) {
  $style = [ordered]@{ fontSize = $size; color = $color }
  if ($bold) { $style['fontWeight'] = 'bold' }
  $c = [ordered]@{ meta = @{ name = $name }; position = [ordered]@{ x=$x; y=$y; width=$w; height=$h }; type = 'ia.display.label' }

    $c['propConfig'] = @{ 'props.text' = @{ binding = [ordered]@{ type = 'expr'; config = @{ expression = $expr } } } }
    $c['props'] = @{ style = $style }
  } else {
    $c['props'] = [ordered]@{ style = $style }
    if ($text) { $c['props']['text'] = $text }
  }
  $c
}
